# 原生 Docker 三方案对照（2026-09-12）

## 结论

1. **NVFP4 原生加载失败是 Definitive 0.1 路径问题，不是 Docker 问题。**  
   Definitive 0.1 在加载权重时无法识别 `lm_head.weight_scale`；同一台机器、同为 Docker 的 Definitive 0.2 能直接选择 `MarlinNvFp4LinearKernel`，FastLLM 也能直接加载，没有转换权重或兼容补丁。

2. **不能笼统地说 NVFP4 只比 FP8 慢 10%。**  
   在固定英文 4096/128 主尺子上，Definitive 0.2 NVFP4 相比 Definitive 0.2 FP8：
   - prefill：`1207.49` vs `1344.61`，慢 **10.2%**
   - decode：`34.56` vs `52.45`，慢 **34.1%**

   但差距不是纯权重格式常数。相同 FastLLM 下 NVFP4 反而比 FP8 快约 **13%**；Definitive 0.2 日志也显示固定提示下 FP8/NVFP4 的 MTP 接受率约为 `55.6%/42.3%`。因此 decode 主要受 **运行时实现 + MTP 接受率 + 提示内容**共同影响。

3. **240K 不是“能空启动”，而是真实跑通。**  
   Definitive 0.2 官方 `fp8kv-240K-mtp3-text-only` profile 成功完成：
   - 输入 `245600` token
   - 输出 `32` token
   - TTFT `378.316s`
   - prefill `649.19 tok/s`
   - 显存约 `20243 MiB/卡`

4. **FP8 官方 128K profile 在当前双 22G 上原生过不了容量门槛。**
   - Definitive 0.1：需要 `4.64 GiB` KV，实际可用 `3.72 GiB`，估算上限 `102400`
   - Definitive 0.2：需要 `4.64 GiB` KV，实际可用 `3.48 GiB`，估算上限 `95200`

   这是 FP16-KV 容量不足，不是模型或 Docker 崩溃。没有缩短 profile 冒充 128K 通过。

## 固定英文主尺子

口径：相同英文 chat token ID，输入 4096、输出 128、`temperature=0`、强制写满、关闭前缀缓存、MTP3；预热后 3 次取中位数。DFlash 使用模型仓库规定的 block size 8，即 7 个 draft token。

| 运行时 / 模型 | 模式 | Prefill tok/s | Decode tok/s | TTFT |
|---|---:|---:|---:|---:|
| Definitive 0.1 FP8 | MTP3 | **1680.57** | 48.41 | 2.437s |
| Definitive 0.1 NVFP4 | MTP3 | 不支持 | 不支持 | 权重加载失败 |
| Definitive 0.2 FP8 | MTP3 | 1344.61 | 52.45 | 3.046s |
| Definitive 0.2 NVFP4 | MTP3 | 1207.49 | 34.56 | 3.392s |
| FastLLM FP8 | MTP3 | 1356.45 | 66.31 | 3.020s |
| FastLLM NVFP4 | MTP3 | 1535.18 | **74.91** | **2.668s** |
| FastLLM FP8 | DFlash7 | 1393.14 | 63.31 | 2.940s |

关键对照：

- Definitive 0.2 FP8 对 Definitive 0.1 FP8：prefill **-20.0%**，decode **+8.3%**
- FastLLM NVFP4 对 FastLLM FP8：prefill **+13.2%**，decode **+13.0%**
- FastLLM DFlash7 对 FastLLM FP8 MTP3：decode **-4.5%**

所以本机固定英文任务上，FastLLM 的原生 NVFP4+MTP3 最快；官方 DFlash7 并未胜过 MTP3。

## 根因判断

### Definitive 0.1 还是 NVFP4 本身

- Definitive 0.1 已进入 Qwen3.5 权重加载，随后报：
  `There is no module or parameter named 'lm_head.weight_scale'`
- Definitive 0.2 对同一只读模型目录原生识别为 `compressed-tensors`，选择 `MarlinNvFp4LinearKernel`
- FastLLM 对同一目录也能原生加载，并在 4K 与 128K 实请求中通过

因此根因是 **Definitive 0.1 的 NVFP4/compressed-tensors 权重加载实现不完整**，不是 NVFP4 权重损坏，也不是模型被转换后才可用。

### Docker 是否影响

Docker 不是加载失败根因：Definitive 0.1、Definitive 0.2、FastLLM 都在同一 Docker/GPU/模型挂载条件下测试，只有 Definitive 0.1 无法识别 NVFP4 参数。性能方面，Definitive 0.1 与 Definitive 0.2 同为容器后仍有明显差异，主要对应运行时版本、CUDA、内核与 MTP 接受率；本轮没有证据支持“Docker 导致 NVFP4 低速”。

### 为什么 NVFP4 有时慢很多

在 Definitive 0.2 固定 chat 提示中，NVFP4 的 MTP 接受率低于 FP8，验证次数增加，decode 被拉低。换到 FastLLM 后 NVFP4 又领先 FP8，证明它不是固定慢 10% 或固定慢 34%。应把“权重量化格式”和“推测解码实现/接受率”分开看。
